## Immediate: finish embedded photos

**Branch:** `embedded-photos` (2 commits, not merged)
**Plan:** `docs/superpowers/plans/2026-08-04-embedded-photos.md`
**Done:** Tasks 1 and 2. **Next:** Task 3, then Task 4.

Per-product comment logs will carry their photos inside the workbook, so someone
reading the log in Autodesk Construction Cloud sees them without the shared folder.

**Already decided — do not re-open:**
- **Thumbnails only** (320px, ~25 KB each, already generated by `savePhoto`). Full-size
  images are ~400 KB, so embedding those would make a 100-photo log ~40 MB and unusable.
  Originals stay in `Photos/`.
- **Per-product logs only.** The Master Log keeps its text filename list so it stays light
  as it accumulates every comment across every product for years.
- **Embed every photo on a comment** — per product even 500 photos is only ~12 MB. A
  generous failsafe cap (2500 images) exists purely to stop a pathological case exhausting
  browser memory mid-export, which would fail the whole thing.

**Task 3 is the tool wiring** in `tools-src/comments-hub.html`: read the thumbnails a
product's rows reference from `Photos/<ref>/thumbs/<file>` into a `Map` keyed
`` `${ref}/${file}` ``, and pass it as the 4th argument to `renderWorkbook`. Constants and
anchor details are in `.superpowers/sdd/photos-model-report.md`.

**The rule that matters:** a missing or unreadable thumbnail must never fail an export —
fall back to the filename text and carry on. A log that fails to generate is far worse than
one with a missing picture.

One open question flagged by the last agent: family workbooks

matches the stated "per-product only" scope — confirm with Harvey before assuming otherwise.

  workshop code. He runs it; then commit `tools/` and push. **`assets/js/` and `tools/`
  must ship in the same push** or the live tools get shared code they were not built against.
- **The P&ID register lost data on 2026-08-03.** Six safeguards now protect it (see
  `docs/superpowers/plans/2026-08-03-pid-register-safety.md`). Do not touch `clearAll`,
  `saveToFolder`, `readRegisterJSON`, the backups or the destructive-save guard without
  strong reason.
- **A failed read must never authorise a write.** That bug class caused the data loss and
  has been fixed in three places. Check for it before adding any new read-then-write path.
- **Harvey is demoing these tools to colleagues who will start using them.** Polish and
  robustness beat architecture right now.
